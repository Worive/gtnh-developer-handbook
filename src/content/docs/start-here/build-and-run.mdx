## Discover tasks before running them

:::note[Repository-specific]
Task names vary. Run only tasks exposed by the selected repository and follow its
README and CI workflow when they differ from this page.
:::

<Tabs syncKey="operating-system">
  <TabItem label="Linux or macOS">

```console
./gradlew tasks --all
```

  </TabItem>
  <TabItem label="Windows">

```console
gradlew.bat tasks --all
```

  </TabItem>
</Tabs>

**Expected result:** Gradle prints the tasks available in this checkout. This
command has been checked against the current
[ExampleMod1.7.10 repository](https://github.com/GTNewHorizons/ExampleMod1.7.10).
If it fails before listing tasks, stop and diagnose the wrapper or dependency
error instead of guessing another task name.

Read [Working with Gradle tasks](/gtnh-developer-handbook/how-to/gradle-tasks/) before using an
unfamiliar task.

## Build and run

If `build` appears and the repository README or CI uses it, run it through the
wrapper. The current [GT5-Unofficial contribution notes](https://github.com/GTNewHorizons/GT5-Unofficial#contribution)
are one repository-specific example that recommends building before IDE import.

If `runClient` appears, it is the usual development-client entry point in
GTNHGradle-based mod repositories. Its registration is visible in the current
[GTNHGradle IDE integration source](https://github.com/GTNewHorizons/GTNHGradle/blob/master/src/main/java/com/gtnewhorizons/gtnhgradle/modules/IdeIntegrationModule.java).
Do not assume it exists in pack, tooling, or older mod repositories.

If IntelliJ provides a **Hotswap** client configuration, use it in debug mode
for quick iteration. After recompiling, choose **Run → Debugging Actions →
Reload Changed Classes** to apply supported changes without restarting the game.
Select the run configuration matching the JDK you need to test.

**Expected result:** a successful build ends with `BUILD SUCCESSFUL`; a run task
starts a development client or prints a specific failure to the terminal and its
log. See [Locate logs](/gtnh-developer-handbook/how-to/locate-logs/) when startup fails.

## Test integration-sensitive changes in the full pack

After the development client passes, build the mod and find its jar in
`build/libs`. Choose the jar without a classifier; `-dirty` may be present when
the working tree has uncommitted changes. Import the latest
[GTNH development build](https://wiki.gtnewhorizons.com/wiki/Dev_Builds) into a
separate launcher instance, replace the packaged mod with that jar, and repeat
the relevant test there. This matters most when the change can interact with
other mods; isolated development runs do not exercise the full pack.

When the project builds and the relevant behavior works, continue to
[your first pull request](/gtnh-developer-handbook/start-here/first-pull-request/).
